# Gemini Build Quick Start

This operator guide is intentionally explicit because the Gemini bundle must remain predictable under mixed evidence and mixed workflow starting points. Router-facing agent descriptions remain concise; detailed behavior lives in specialist instructions and maintained knowledge.

## Test-only boundary

A branch-built or otherwise unpromoted bundle is a test-agent artifact. Load it only into a separate Gemini draft/test agent. Do not treat successful compilation, static validation, or packaging as live/main promotion.

## What changed in this major-version wave

This major-version build expands the bundle from a narrower alert-triage-plus-collector-orchestration posture into a more explicit end-to-end investigation assistant. The active source tree now assumes:
- the operator may start from an alert
- the operator may start from collector output
- the operator may start from retrieved artifacts
- the operator may start from an IOC package in mixed format
- the operator may need a targeted collection design instead of a broad baseline
- the operator may need a recurring weekly USB violations report workflow from structured CSV, XLSX, pasted table, or copied spreadsheet data
- the operator may need a richer shared attachment set that explains the collector and Gemini runtime lines in stand-alone detail

The active agent topology includes eleven sub-agents:
1. Session readiness and intake
2. Environment, coverage, and schema mapping
3. Alert-family classification and known-benign-technology differentiation
4. Evidence, provenance, and timeline analysis
5. Query planning and syntax guard
6. DCOIR collector execution and bundle workflow orchestration
7. DCOIR collector artifact interpretation and report extraction
8. IOC parsing and evidence-grounded public enrichment planning
9. Targeted collection design and evidence-gap reduction
10. Output-contract consistency guard and report composition
11. USB violations report composition

The active shared attachment set includes twenty-eight knowledge pages:
- 01 through 11 preserve core, collector, workflow, troubleshooting, FAQ, prompt-design, and IOC-enrichment guidance
- 12 through 14 preserve Gemini runtime source-tree, topology, and output-contract guidance
- 15 through 16 preserve collector EXE/runtime and feature/output-contract guidance
- 17 through 28 preserve Elastic field, response-action, and sharded OSQuery references

## Routing and handoff model

- Agent descriptions use the concise Use when / Do not use when / Returns contract.
- Prime chooses a branch-specific route rather than forcing every request through one universal sequence.
- Internal specialists 01 through 09 return `common_handoff_envelope_v1`, with agent-specific results under domain_payload.
- Prime applies route-loop guards and sends the reconciled state to exactly one terminal output owner.
- Output Contract Consistency Guard and Report Composer handles ordinary analyst-facing output; USB Violations Report Composer handles explicit USB reporting only.

## Source and build provenance

The maintained source version is the manifest `bundle_version`. A workflow override or timestamp is the build identifier. Record the test artifact using all of these values:
- source branch or ref
- source head SHA
- workflow run ID
- artifact name
- delivery ZIP SHA256

Do not treat a build identifier as the semantic source version, and do not infer current provenance from an older artifact filename.

## Starter prompts

Starter Prompt 1:
"I am pasting an Elastic alert and I want the single best next triage command. Assume I can run KQL, ESQL, and Elastic response actions. Follow the exact continue format and do not skip the singular command."

Starter Prompt 2:
"I already ran the collector and I am uploading the DCOIR upload summary and the analyst follow-up queue. Interpret what the collector is telling us, tell me the best next file or artifact to upload, and keep the case in collector-aware mode."

Starter Prompt 3:
"I have a mixed IOC package in CSV, PDF text, and copied notes. Parse the indicators, classify them by type, show them in analyst-facing grouped form, then give me the narrowest useful KQL, ESQL, response-action, and collector follow-up options."

Starter Prompt 4:
"I need to prepare the weekly USB violations report. I will provide the USB violations source data and last week's overall count. Validate the data conservatively, ask before guessing, split NIPR/SIPR if needed, and draft the exact plaintext email blocks."

## Build process

1. Edit the maintained `knowledge/*.md` files first when the shared knowledge layer changes.
2. Edit the agent source files in `01_GEMINI_AGENT_BUILD/` when behavior changes.
3. Update the manifest required-files inventory whenever the attachment set changes.
4. Update `00_START_HERE/Agent_Attachment_Map.md.txt` whenever the attachment inventory or purpose changes.
5. Rebuild through the governed GitHub Action or governed build script.
6. Review the source version, build identifier, head SHA, workflow run, artifact name, ZIP digest, and JSON reports before treating the bundle as test-ready.

## Validation focus

Every serious review of the current bundle should explicitly cover:
- branch-specific route selection and specialist order
- common handoff-envelope preservation and loop suppression
- starter prompt behavior
- collector artifact interpretation
- mixed-format IOC parsing
- targeted collection recommendations
- false-positive-aware handling of known enterprise products
- SINGULAR TRIAGE COMMAND consistency
- leadership-writeup behavior
- weekly USB violations report behavior, including Friday/date-window handling, conservative CSV/XLSX parsing, missing-field checks, SNOW-prefix classification, NIPR/SIPR split output, and exact plaintext recipient, subject, and body blocks
- attachment-map, manifest, and maintained-knowledge alignment
- source-versus-build provenance readback
- ordinary direct generation/build behavior when the shared knowledge set changes
