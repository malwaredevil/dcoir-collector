DCOIR Gemini Creation Pipeline v1.1.0

Purpose
- Define the governed create-and-ship path for the operator-facing Gemini bundle after the stored-source compile model was adopted.
- Make the Gemini bundle manifest the explicit source of topology truth for the prime agent and sub-agent set.
- Keep future topology changes governed, reviewable, and repeatable.

Current authority and source model
- Shared behavior modules under `project_sources/agent_runtime/behavior_modules/` are canonical behavior authority.
- `Behavior_Module_Manifest.json` maps those modules to checked-in Gemini adapter outputs with SHA-256 integrity.
- `project_sources/gemini/bundle_source/` remains the Gemini topology and packaging tree; its Prime chunks and specialist files are generated adapters.
- `Gemini_Bundle_Source_Manifest.json` remains the compile contract and now also carries the explicit topology contract.
- Ordinary shipment remains validation plus compilation, not ad hoc regeneration.

Topology truth rules
- The manifest is the explicit source of truth for:
  - the prime-agent file
  - the listed sub-agent files
  - the expected sub-agent count
  - the required-file set that must ship
- Validation must compare the manifest topology against the actual source-tree contents and fail on drift.
- Workflow required-surface validation must read Gemini bundle required files from the manifest rather than duplicating hardcoded sub-agent file lists.

Required behavior when adding or removing sub-agents
1. Add or retire the canonical shared specialist module and its behavior-module mapping.
2. Update the Gemini manifest topology section.
3. Update `required_files` in the Gemini manifest.
4. Materialize the Gemini adapter.
5. Update the generated index and operator guidance when topology changed.
6. Re-run adapter checks, validation, and build.
7. Do not treat a new specialist as active topology until both shared mapping and Gemini topology reflect it.

Workflow
1. Confirm the current startup-pack-first operating contract and authority surfaces.
2. Edit affected shared behavior modules.
3. Refresh declared SHA-256 values and materialize generated Gemini adapters.
4. Update the Gemini manifest topology and required-file contract when topology changed.
5. Run `materialize_agent_behavior_adapters.py --check`.
6. Run `validate_dcoir_gemini_bundle.py`.
7. Run `build_dcoir_gemini_release.py`.
8. Review the workflow summary and uploaded build artifacts.
9. Ship the compiled zip only after the validation path passes.

Hard rules
- Do not let folder discovery silently replace the manifest as topology authority.
- Do not add or remove sub-agents by file drop alone.
- Do not let the workflow report a successful bundle when manifest topology and source-tree contents drift.
- Do not let the release builder proceed when shared modules and checked-in Gemini adapters drift.
- Keep the validation summary explicit enough that the operator can see the manifest-listed and discovered sub-agent counts.

Recommended next move
- Use the manifest-driven topology contract for the larger major-version Gemini runtime bundle, then validate the current manifest-listed sub-agent topology through the associated Actions workflow before tomorrow's functionality test.

Prime-agent generated runtime topology note
- The editable Prime behavior is the ordered shared module set declared by `Behavior_Module_Manifest.json`.
- The chunk set under `01_GEMINI_AGENT_BUILD/prime_agent_chunks/` is a checked-in generated adapter surface ordered by `Prime_Agent_Chunks_Manifest.json`.
- `01_GEMINI_AGENT_BUILD/Prime_Agent_DCOIR_Gemini_Orchestrator.md.txt` is a generated runtime artifact assembled from the chunk manifest before validation and compile.
- The generated runtime prime-agent file must appear in the final Gemini Enterprise bundle as one coherent prompt file. Source-only chunk files and the chunk manifest must not ship in the final Gemini delivery ZIP.
- Build and validation lanes must reassemble before judging the Gemini agent and must inspect the final ZIP for source-only leakage.
