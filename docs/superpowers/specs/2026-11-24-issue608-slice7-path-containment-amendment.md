## 2. Decision and scope

Prefer a narrow fail-closed resolver over either retaining the vulnerable lexical check or replacing the report-writing subsystem. Reject Windows path ambiguities and filesystem links even if a particular link happens to target an in-tree location. This policy is easier to audit than allowing arbitrary resolved link targets and covers the observed defect without changing the public action interface. Preserve normal nested outputs, existing regular output files, normalized slash spelling, whole-input ordinary whitespace trimming, suffix case handling, the two returned fields, and prior rejection diagnostics for the existing cases. Deliberately reject previously tolerated ambiguous paths that cannot be safely and consistently interpreted. Do not introduce a global path abstraction, change other actions, change the post-hoc Python validator, relax gates, add dependencies, or edit workflow YAML/action.yml.

Keep the original five-file implementation scope: the duplicate-function action entrypoint, its new definitions-only sibling helper, its native PowerShell test, the existing Python test driver, and the action README; regenerate only required canonical inventory/analyzer evidence. The helper remains the single owner of the two public functions. Any small private helper needed for literal component inspection must live in the same file, have a distinct name, and be exercised through the public resolver. Do not create another behavioral mirror. The action remains report-only and the independent validator remains unchanged.

## 3. Resolver and write-boundary contract

1. Keep existing input validation in its original diagnostic order: required/nonblank, control characters before trim, absolute/drive-relative roots, parent traversal, case-sensitive collector prefix, and expected suffix. Preserve existing public signatures and valid FullPath/RelativePath results. After these checks reject ambiguous internal path components: empty or dot-only components, trailing spaces or periods within a component, colon/stream syntax, illegal Windows filename characters, and reserved DOS device base names (case-insensitive, including extensions, CONIN$/CONOUT$, and COM/LPT digit variants recognized by Windows). Treat device aliases and equivalent ambiguous names as disallowed before any filesystem access. Safe names containing ordinary internal spaces, hyphens or embedded double dots remain accepted. Document intentionally tightened syntax.
2. Derive absolute candidate and allowed collector root using literal filesystem path operations from the trusted checkout root. Require exact component-boundary containment below project_sources/collector, not merely under repository root or a prefix lookalike. Use appropriate path comparison for the platform (Windows ordinal ignore-case for resolved paths; original input subtree spelling remains case-sensitive). Use the same trusted root and current-location contract as the existing entrypoint; verify consistency, and reject a non-filesystem or invalid anchor. The checkout root is the trust anchor, not an assertion that its ancestors on the host volume are controlled by this action.
3. Inspect the existing checkout root, project_sources, collector, each existing nested directory, and any existing output leaf by literal path, in parent-to-child order. Reject reparse-point attributes without traversing the linked component, including junctions, symbolic links and dangling links. Require normal directories for ancestors and a regular file or not-yet-existent path for the leaf. Missing nested components are allowed only beneath a verified normal directory; distinguish genuine not-found from permission, IO, or metadata failures. Do not use Test-Path false or a blanket catch as proof that a component is absent. Use native filesystem metadata and terminating literal lookups, and verify their behavior in Windows tests. Existing file hard links are a distinct alias class: reject hard-linked output leaves using reliable native metadata, with a mandatory Windows fixture proving the detection. If the supported runtime cannot establish that case reliably, stop and revisit the design rather than passing a false containment claim. Never resolve or open an outside report target. Do not write during resolution.
4. Keep both output paths validated before the action creates any report. Recheck the same shared guard immediately before each output write, including after any required directory creation; use literal directory creation and literal file writes. Avoid provider wildcard interpretation of otherwise valid file names. Preserve existing JSON and Markdown serialization, encoding, schema, names, defaults and normal write ordering. For both invalid-JSON/safe-Markdown and safe-JSON/invalid-Markdown inputs already present before execution, neither output may be written. A subsequent unexpected filesystem mutation must fail rather than knowingly follow a link.
5. Security boundary: this is protection against statically present filesystem aliases and invalid path input within a trusted, isolated Windows checkout. Rechecking narrows but does not eliminate time-of-check/time-of-use races. This is not a handle-based OS sandbox, a guarantee against hostile concurrent filesystem mutation, or a claim of physical containment on every filesystem. Do not claim broader protection. If fixture evidence exposes another in-scope alias bypass or a safe-output regression, disposition before readiness; do not weaken assertions.
